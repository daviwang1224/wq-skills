# 信源读取与路由策略

## 文件定位

本文只定义如何定位、筛选、读取和判定信源，不保存任何产品、组织、人员、项目、决策、观点或历史总结正文。所有事实和判断均在技能运行时从原始文件或实时系统读取，避免形成重复信源。

## 一、本地知识库启动

1. 将用户指定目录作为工作目录；未指定时使用 `D:\2_project\wq-work-wiki`。
2. 按知识库根 `AGENTS.md` 的要求完成启动读取和配置解析，不在本文件复述这些规则。
3. 根据实际访问区域继续读取对应区域的 `AGENTS.md`。区域规则与本文件冲突时，以区域规则为准。
4. 只读取完成本次月度总结所需的文件，不把整个知识库一次性装入上下文。

## 二、读取目标月份飞书日志

进入该阶段前，读取 `$lark-doc` 的 `SKILL.md` 和 `docs +fetch` 参考，使用用户身份读取指定 Wiki 文档。

### 1. 先获取结构

先执行目录读取，确认年份、月份标题、物理顺序和相邻边界：

```powershell
lark-cli docs +fetch --doc '<工作日志URL>' --scope outline --max-depth 3 --as user
```

不要仅凭当前日期假设文档一定存在对应月份。

### 2. 确定月份边界

- 找到目标年份下与目标月份准确对应的月份标题。
- 同时寻找文档物理顺序中紧邻目标月份的前后月份标题。
- 工作日志内部可能包含与月份标题同级的其他标题，因此不能默认使用 `section` 就能覆盖整月内容。
- 优先使用月份标题之间的 `range` 读取完整区间，并在解析时排除作为结束边界的相邻月份内容。
- 如果目标月份位于文档首尾、缺少相邻月份边界，先依据 outline 中可见的顶层块确定可用端点；仍无法可靠截取时，读取覆盖目标月份的最小更大范围，再按明确月份标题裁剪。

示例命令形态：

```powershell
lark-cli docs +fetch --doc '<工作日志URL>' --scope range --start-block-id '<目标月份标题ID>' --end-block-id '<相邻月份标题ID>' --detail simple --doc-format markdown --as user
```

`range` 可能包含两个端点，必须在生成事实底稿前移除不属于目标月份的边界内容。

### 3. 判断日志完整性

读取后检查：

- 是否存在目标月份标题；
- 是否只有月初计划而没有过程或结果记录；
- 是否混入相邻月份内容；
- 是否出现嵌入表格、引用文档或其他资源，需要按 `$lark-doc` 的资源路由继续读取；
- 是否存在明显截断、权限不足或响应降级提示。

信息不完整时继续使用已有证据生成有限结论，并明确缺口；不要用历史总结补齐当月事实。

## 三、读取稳定上下文

- 月度总结通常跨越角色、产品、组织、团队、研发流程和判断原则。按知识库根 `AGENTS.md` 的稳定上下文规则，从 `3-work/0-context` 读取完成本次任务所需的 Markdown 文件。
- 当用户明确要求“读取全部个人上下文”时，读取该目录当前存在的正文文件，而不是在技能中维护一份固定文件清单。
- 只引用运行时读到的内容；本技能及参考文件不保存这些内容的摘要副本。

## 四、读取历史总结与年度主线

1. 先读取 `3-work/5-summary-plan/index.md`，由索引发现现有总结和规划，不在技能中固化文件列表。
2. 优先选择最近一份与目标产物同类型、结构最接近的月度总结或工作述职，用于学习篇章组织、表达节奏和信息密度。
3. 读取目标年份的年度工作规划与推进文档，用于理解年度主线、跨月事项和已有风险，但其中的计划与历史状态不能直接写成目标月份完成事实。
4. 只有在月度样例不足时，才按需读取季度、半年或年度总结；不要为模仿风格全量读取全部历史文档。
5. 如果目标月份已有正式总结，先确认用户是在修订、分析还是重新生成，避免把既有总结误当作原始日志。

## 五、读取决策、个人思考和外部知识

该阶段主要服务“工作亮点和问题分析”，遵循先索引、后正文，先稳定信源、后补充材料的顺序。

1. 从 `3-work` 的索引或对应目录发现与当月工作主线相关的正式决策、风险、复盘和 Playbook。
2. 从 `2-thinking/index.md` 按主题和时间筛选相关个人思考。若索引表明某项稳定结论已经转入 `3-work/0-context`，优先使用稳定上下文；除非需要观点形成过程，否则不重复读取原思考。
3. 需要外部管理、产品或方法框架时，从 `1-knowledge/index.md` 或 `1-knowledge/wiki` 的索引进入相关页面。
4. 只有需要核对外部证据时才读取 `1-knowledge/raw`。
5. 默认不读取 `0-inbox`；只有用户明确指定时才将其作为待确认材料使用。

选择正文时以当月日志中出现的项目、产品、流程、质量、组织和管理主题为检索线索，不按目录全量加载。

## 六、信源作用与冲突处理

不同信源承担不同作用：

- 目标月份飞书日志：提供当月事项和记录时点；
- 正式仓库、任务系统或实时系统：在用户要求核验当前状态时提供更高时效事实；
- `3-work`：提供已确认的个人工作上下文、决策和管理规则；
- `2-thinking`：提供已确认的个人观点，不自动等同于正式规则；
- `1-knowledge/wiki`：提供外部知识和分析框架，不能证明当月事项已发生；
- 历史总结：提供写作样例和历史边界。

发生冲突时，不自行合并或选择更顺眼的说法。记录冲突双方、时间和来源；能够通过更高权威或更新来源核验时再下结论，否则在输出中降低确定性或明确保留未知。

## 七、内部事实底稿

写作前在上下文中建立轻量事实底稿，不要求输出或落盘。每条至少包含：

- 事项或主题；
- 来源及记录时间；
- 所属月份；
- 状态：已完成、推进中、计划中、无法确认；
- 已产生的结果或证据；
- 对交付、产品或团队的影响；
- 仍需核验的问题。

同一事项在多条日志中重复出现时进行合并，保留最新进展和必要的演变过程，不按日志条数放大工作价值。
